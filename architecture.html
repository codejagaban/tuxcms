Tenant Identification (3 strategies)

1. Domain / Subdomain

Each website gets a subdomain or custom domain.
acme.tuxcms.com or www.acme.com

Recommended for public sites

2. API Key Header

Frontend sends X-Tenant-Key header to identify which website's data to serve.

Recommended for headless

3. Auth-Based

Authenticated user's tenant_id determines scope. Used for the admin dashboard / CMS panel.

Admin panel access

Application Layer

TenantScope (Global Scope)

Auto-applied to all tenant-aware models. Every query automatically includes WHERE tenant_id = ?. No data leakage between tenants. Applied via BelongsToTenant trait.

Data isolation layer

Middleware Stack

ResolveTenant — Identifies tenant from domain/header/auth
EnsureJsonResponse — Forces API JSON output
auth:sanctum — Token authentication
CheckTenantOwnership — Verifies user belongs to tenant

User & Role Hierarchy

Super Admin

Global access across ALL tenants. Can create/delete tenants, manage billing, impersonate users, view analytics across all sites.

Global scope (no tenant_id filter)

Tenant Owner

Owns a specific website/tenant. Full control over their site's pages, menus, forms, settings, media. Can invite team members.

Scoped to their tenant

Tenant Editor

Invited by tenant owner. Can edit pages, manage form submissions, upload media. Cannot change site settings or invite others.

Scoped + limited permissions

Database Schema (key tables)

tenants

  • id (PK)
  • name
  • slug (unique)
  • domain (unique, nullable)
  • api_key (unique)
  • owner_id → users.id
  • plan (free/pro/enterprise)
  • settings (JSON)
  • is_active (boolean)
  • timestamps

users

  • id (PK)
  • name, email, password
  • is_super_admin (boolean)
  • timestamps

tenant_user (pivot)

  • tenant_id → tenants.id
  • user_id → users.id
  • role (owner/editor)
  • timestamps

pages

  • id (PK)
  • tenant_id → tenants.id
  • title, slug, content, excerpt
  • template, status, order
  • parent_id, is_homepage
  • custom_fields (JSON)
  • author_id → users.id

page_sections

  • id (PK)
  • tenant_id → tenants.id
  • page_id → pages.id
  • key, type, title, content
  • data (JSON), order
  • is_visible

menus / menu_items

  • tenant_id → tenants.id
  • name, slug, location
  • items: title, url, target, order
  • parent_id (nested)

forms / form_submissions

  • tenant_id → tenants.id
  • name, slug, fields (JSON)
  • submissions: data (JSON)
  • notification_email
  • ip_address, is_read

settings

  • tenant_id → tenants.id
  • key (unique per tenant)
  • value (JSON)
  • group

Implementation Approach

Why Single DB with tenant_id?

Simpler — No managing multiple databases or connections per tenant

Scalable — Handles thousands of small-to-medium sites efficiently

Cost-effective — One database instance, one deployment

Easy migrations — Schema changes apply to all tenants at once

Global scope — Laravel's global query scope auto-filters every query by tenant_id, preventing data leaks
